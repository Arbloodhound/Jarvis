# DIAG button fix — 2026-10-20

**Symptom, as reported by the owner (Pixel 10 Pro XL, GrapheneOS, Android 17, latest `main`
build — merged tree, UI rework included):** "the DIAG button is broken still." No further
detail was given, so the button and the capture behind it were audited end to end
(`ui/DiagnosticFab.kt`, `diag/LiveDiagnostic.kt`, `diag/SystemTrace.kt`, and the FAB's
placement in `MainActivity.kt`, all read on `main` @ `b7ad77af`). Four defects were found —
the first one alone reproduces "broken" on the owner's normal workflow — plus one hardening
gap. All are fixed on branch **`claude/diag-button-fix`**; nothing here is on `main` yet.

Line numbers below are the pre-fix lines on `main`.

---

## Defects found

### D1 — STRONGEST: stopping a capture wedges the button for the life of the process
`diag/LiveDiagnostic.kt`, the `finally` block of the capture job (lines 100–105), with
`stop()` at line 109.

`start()` sets `running = true` (line 65) and launches the capture. Stopping is
`job?.cancel()`. Cancellation throws `CancellationException` out of the poll loop's
`delay()`, and the `finally` then runs:

```kotlin
remainingSec.intValue = 0
val file = withContext(Dispatchers.IO) { writeReport(...) }   // line 102
lastFile.value = file                                          // line 103
running.value = false                                          // line 104
```

A cancelled coroutine cannot complete a suspension: `withContext` throws
`CancellationException` instead of delivering a result, so lines 103–104 **never execute**.
`running` stays `true` forever, `lastFile` stays null — a frozen, still-pulsing green
"REC 0:00", no file, no SEND/RESET. Every later tap goes through `toggle()`, sees
`running == true`, and calls `stop()` on the already-dead job: a no-op. The button is dead
until the app process restarts.

This hits the documented workflow exactly: captures are meant to be short and ended with a
tap ("tap again to stop early"; REAL_TASKS.md: "For any Fail, tap DIAG right after it"). A
capture left to run the full 15 minutes exits the loop *without* cancellation, the
`finally` works, and SEND/RESET appear — which is how this survived: the long path works,
the normal path wedges. (This is also plausibly why the button was "broken **still**" after
the 2026-10-20 SEND/RESET fix: that fix addressed being stuck *on* SEND; the wedge is one
step earlier, at the stop.)

**D1b, same class:** the Downloads create — `withContext(Dispatchers.IO) {
createInDownloads(...) }` at line 77 — sat *outside* the `try`, so a stop landing during
start-up killed the job before the `try/finally` was ever entered: `running` stuck `true`,
countdown stuck at 900, no cleanup at all.

### D2 — an exception mid-capture could crash the app
`diag/LiveDiagnostic.kt`, capture body (lines 79–99), scope at line 58.

The poll loop calls `RamReport.snapshot`, `SystemTrace.snapshot`, `header()` /
`KitReport.hasCrash` every 8 seconds with no guard at the call site. The scope is a root
`CoroutineScope(SupervisorJob() + Dispatchers.Default)`: an uncaught exception in a root
`launch` is passed to the thread's default uncaught-exception handler — on Android that
kills the process. One bad poll could take the whole app down mid-diagnostic; even short of
a crash, the capture died silently from the owner's point of view.

### D3 — flaky taps: drag and tap detectors fight over the same press
`ui/DiagnosticFab.kt`: `detectDragGestures` on the outer box (lines 73–75) vs
`detectTapGestures` on the circle inside it (lines 92–95), two competing `pointerInput`s.

Any finger drift past the touch slop — normal on a 60 dp one-handed target — makes the
parent's drag detector start consuming moves (`change.consume()`), which cancels the
child's `waitForUpOrCancellation`: the tap is silently eaten and the button only nudges.
Taps worked only with a perfectly still finger. Separately, the inner detector was keyed on
`(running, file)`, so it was torn down and rebuilt on every state flip — a needless
mid-gesture restart hazard.

### D4 — SEND could throw out of its tap handler
`diag/LiveDiagnostic.kt`, `share()` (line 188).

`FileProvider.getUriForFile` throws `IllegalArgumentException` for a file outside the
configured roots, and `startActivity` can throw; `share()` was called straight from the SEND
chip's `onTap` unguarded, so any failure crashed the app out of the tap and read as "SEND is
broken". Latent while reports only ever lived under `cacheDir/exports` (which
`res/xml/file_paths.xml` covers) — but D5's new fallback makes a non-covered location
reachable, so this had to be closed with it.

### D5 — no fallback if the share-copy write failed
`diag/LiveDiagnostic.kt`, `writeReport()` (line 158).

The shareable copy was written to exactly one location (`cacheDir/exports`). If that write
threw — a stray file sitting where the `exports` directory should be, storage pressure —
`writeReport` returned null: the capture "finished" with `lastFile == null`, no SEND/RESET,
and the report survived only in Downloads/Jarvis (if that write had worked).

## Checked and cleared (not defects)

- **FAB placement / z-order:** `MainActivity.kt` (lines 72–79) draws `DiagnosticFab` as the
  last child of the root `Box`, over every screen, ungated. The UI rework never touched this
  placement; the button is not covered.
- **Downloads/MediaStore under GrapheneOS/Android 17:** `createInDownloads` is
  try/caught → null on failure; the per-minute saves then skip, but the final cache copy
  still became `lastFile`, so a Downloads failure alone could not wedge the button. Not the
  bug (D1 was).
- **Coroutine scope death:** the scope is a standalone supervisor scope on the object; it
  cannot die independently. Process death resets all DIAG state, and the per-minute
  Downloads save preserves the partial capture. By design.
- **SEND/RESET chips:** stable `pointerInput(label)` keys; their consumed presses are now
  explicitly honored by the new outer detector.
- **`SystemTrace`:** all I/O internally guarded, parsers pure. Not implicated.

## Changes made (branch `claude/diag-button-fix`)

### `diag/LiveDiagnostic.kt` — commit `70b5c6220d`
- `finally` now writes the report under `withContext(NonCancellable + Dispatchers.IO)`
  (D1). The state reset after it — `lastFile`, then `running = false` — now executes on
  **every** exit: natural end, early stop, or failure. Comment in code explains why
  `NonCancellable` is load-bearing.
- The `try` now wraps the whole capture from the Downloads create onward (D1b);
  `name`/`saved` are hoisted above it so the `finally` can always reach them.
- Added `catch (CancellationException) { throw e }` (finally still runs) and
  `catch (Exception)` around the capture: an error is appended to the report text
  ("diagnostic capture ended early: …") and the capture finishes with what it has,
  instead of propagating to the default handler (D2).
- `writeReport`: the share copy is attempted at `cacheDir/exports` (FileProvider-covered,
  tried first), then `cacheDir`, then `filesDir`; first success wins, so a finished
  capture still ends with `lastFile` set (D5). Note: `filesDir` is outside
  `file_paths.xml`, so SEND of that last-resort copy no-ops via the D4 guard — the
  Downloads/Jarvis copy is then the one to send by hand.
- `share()`: the whole body is guarded with try/catch — a failed share can no longer
  crash the app out of the SEND tap (D4).
- Imports added: `kotlinx.coroutines.CancellationException`, `kotlinx.coroutines.NonCancellable`.

### `ui/DiagnosticFab.kt` — commit `7f9a10121a`
- The nested drag/tap pair is replaced by ONE detector on the outer box
  (`Modifier.diagGestures`, private): a release that never passed the touch slop is a
  tap; past the slop it becomes a drag (moves consumed, no tap fires) (D3). Plain taps
  now register every time, with or without finger drift.
- The circle is purely visual now — no `pointerInput` of its own; the detector is keyed
  on `Unit` and reads callbacks/state through `rememberUpdatedState`, so it never
  restarts mid-gesture or on a state flip.
- In the finished (SEND/RESET) state the outer detector is drag-only, so a stray press
  between the chips cannot start a new capture over an unsent file; chips keep their
  own tap handlers, and an up a chip consumed is never treated as an outer tap.
- Comment-only fix: the class KDoc said the capture runs "5 minutes"; `DURATION_SEC`
  has been 900 (15 minutes) since 2026-10-20. Doc now matches the constant. No
  behavior change.

## Deliberately NOT changed

- `DURATION_SEC` (900), `POLL_MS` (8000), the log-tag list, the every-minute
  Downloads/Jarvis save, the report format and file naming — untouched.
- Public surface unchanged: `LiveDiagnostic.toggle/start/stop/running/remainingSec/
  lastFile/share` and the `DiagnosticFab()` signature — `MainActivity` and everything
  else keeps compiling against them.
- Every user-visible string is byte-identical ("DIAG", "REC", "SEND", "RESET", the
  countdown format); sizes (60/84 dp, chips 64 dp), colors (cyan `#22D3EE` accent, near-
  black `#111417`, recording green) and the drag-offset behavior are as they were.
- No tests added: the fixed logic is coroutine-state and Compose-gesture behavior,
  which the current JVM test setup cannot exercise; the suite expectation stays 1644.
